# Архитектурные варианты из обсуждений (L0 + Fabric)

Статус: исследовательская фиксация рассуждений (не канон, не реализационный контракт).

Дата фиксации: 2026-02-09.

Назначение:
- сохранить две согласованные версии архитектурного мышления;
- не потерять полезные формулировки при переходе к коду;
- отделить рабочую модель ближайших фаз от дальней target-модели.

## 1) Вариант A: L0 как живой поток, Ln как подписчики

Короткая формула:
- DETM = поток + подписчики.
- `L0` = единственный постоянно тикающий слой.
- `Ln` = слои интерпретации/коарсенинга, читающие `L0` через проекции.

Ключевые тезисы:
- Мир задаётся динамикой, а не архивом состояний.
- Состояние - это срез, объект - устойчивый паттерн потока.
- `L0` соответствует “оперативной” динамике (условный RAM-слой).
- Устойчивые инварианты/паттерны соответствуют “долгой памяти” (условный SSD-слой).
- `Ln` не обязаны видеть полный `DETMState`; предпочтителен контракт артефактов.
- Обратное влияние `Ln` на `L0` допустимо как полевое воздействие, а не прямой write state.

Уравнения (рабочая форма):
- `L0(t+1) = F(L0(t), influence_t) + Sum_i feedback_i(t)`
- `Ln_i(t+1) = G_i(project_i(L0(t)), local_state_i(t))`

Практический смысл:
- Эта версия хорошо ложится на текущий runtime (`Session/Bus/Scheduler`).
- Это near-term модель для фаз 2-5 roadmap.

---

## 2) Вариант B: сеть автономных узлов (Node/Fabric/Protocol)

Короткая формула:
- Система = множество узлов + подписки + протокол обмена `OuterFields`.
- Каждый узел - локальная DETM-модель со своим state/time.

Ключевые тезисы:
- Уровни и узлы обмениваются не `DETMState`, а границей (`OuterFields`).
- Вычисление возникает как устойчивые паттерны межузловых взаимодействий.
- `Refine` включается при потере предсказуемости границы/инварианта.
- Fabric маршрутизирует сообщения, не являясь “центральным мозгом”.
- Наблюдатель читает артефакты read-only.

Уравнения (сетевая форма):
- `state_j(t+1) = H_j(state_j(t), OuterFields_in_j(t))`
- `publish_j -> OuterFields_out_j(t)`
- `Fabric routes OuterFields_out_j -> subscribers`

Практический смысл:
- Это дальняя target-модель (после стабилизации `LevelPolicy/refinement`).
- Требует отдельного межузлового контракта и runtime-контуров, которых пока нет в коде.

---

## 3) Что из вариантов нельзя трактовать как “уже реализовано”

- Постоянное SSD-хранилище паттернов/операторов.
- Явный RAM-cache недавних паттернов как отдельная подсистема.
- Полноценная fabric-сеть автономных NodeRuntime.
- Полный цикл `predict -> refine -> collapse -> persist` как production pipeline.

Это остаётся target/design-слоем до реализации отдельных модулей.

---

## 4) Нормализация для текущего проекта

Для текущей кодовой базы DETM обе версии используются так:
- Вариант A - как рабочая архитектурная рамка ближайших фаз.
- Вариант B - как целевое направление, которое не должно подменять runtime раньше времени.

Операциональное правило:
- сперва стабилизировать `LevelPolicy`, `refinement`, `PatternStore/PatternCache`,
- затем переходить к самостоятельному `Node/Fabric` контуру.

---

## 5) Минимальный список переносимых решений в код

1. Интерфейс `PatternStore` (file-backed stub, версионирование артефактов).
2. `PatternCache` (LRU/TTL по сигнатурам и инвариантам).
3. Lookup паттерна до дорогого `refinement`.
4. Контракт межузловых сообщений на базе `OuterFields` (отдельным этапом).

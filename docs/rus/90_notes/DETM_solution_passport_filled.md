Статус: живой артефакт / decision map

---

## 0) Идентификаторы

- Проект: `DETM`
- Паспорт: `SP-DETM-0001`
- Дата: 2026-01-22
- Статус: active (draft)

## 1) Контекст

### 1.1 Проблема

Проект DETM содержит каноническое L0‑ядро и runtime‑обвязку, но следующий этап требует:
- переноса основного UX/инструментария на napari + Qt (без лицензий),
- жёсткого разделения: состояние/динамика/поиск/переходы уровней живут на GPU,
  а наружу уходит только “скомпиллированный” результат (артефакты, метрики, сигналы),
- постепенного внедрения многоуровневости (coarsen/refine/LevelPolicy) и протоколов подписок.

Критичный риск текущего стека: неявные CPU-копии полей и “вмешательство наблюдателя” через полное состояние.

### 1.2 Текущее положение

Что уже есть:
- `detm/runtime/api/*` как L0 API (`reset/step/digest/serialize/deserialize`).
- Torch/Numpy backend.
- Сериализация state (msgpack + npz).
- Визуализация/инструменты (Tk + TCP daemon) как первые прототипы.
- Napari-прототип viewer (не канон).

Что мешает:
- “observables” и диагностика часто провоцируют полную материализацию полей на CPU.
- UI/оркестрация живут рядом с `detm/`, что затрудняет чистоту ядра.

---

## 2) Цели и критерии успеха

### 2.1 Цели

- GPU-first: DETMState и все вычисления динамики/метрик остаются на GPU.
- Публикация наружу: только артефакты (OuterFields, signature/summary/events/quality), без полной копии state по умолчанию.
- UI napari/ComfyUI: read-only подписчики, работающие по контракту подписок.
- Подготовка к уровням: `BaseTick(Lmin)` и окна наблюдения, `OuterFields` V1 как граница уровня.

### 2.2 Не-цели

- Не делаем “ИИ-агента”, который управляет миром.
- Не превращаем L0 DETM в биологическую/социальную теорию.
- Не оптимизируем всё под многопроцессный GPU IPC на первом шаге.

### 2.3 Definition of Done (для ближайшего этапа)

- `step()` не копирует поля на CPU по умолчанию.
- Тяжёлые CPU-аналитики включаются только явно (opt-in).
- Определена схема `OuterFields` V1 и добавлен вычислитель/интерфейс в коде.

---

## 3) Ограничения (жёсткие)

- UI стек: napari + PySide/Qt (без коммерческих лицензий).
- “Нет копии DETMState на CPU по умолчанию”.
- Детерминизм: фиксированный seed + фиксированная последовательность influence → воспроизводимый результат.
- Визуализация — подписчик, не часть L0.

## 6) Допущения

- Сначала поддерживаем Torch/CUDA (и Torch/CPU как fallback); остальное держим в уме.
- Внешний контур (napari/ComfyUI) не требует доступа к state, ему достаточно артефактов.
- Отношения уровней на первом шаге задаются окнами наблюдения/классами периодов, без тонких `ε`.

## 7) Выбранная модель/архитектура

### 7.1 Ключевая идея

Ядро считает динамику и “видимые” артефакты на GPU; наружу публикуются только компактные результаты,
а любые тяжёлые копии/preview включаются по подписке и не являются частью канона.

### 7.2 Компоненты

- `detm/core` + `detm/runtime`: L0 динамика, состояние, backend, минимальный API.
- Анализаторы: GPU-first модули, выдающие `OuterFields`/метрики.
- UI: napari как подписчик (read-only), ComfyUI как thin-client.

### 7.3 Границы ответственности

- GPU: `DETMState`, шаги, подписи/summary, OuterFields, консенсусные метрики.
- CPU: только артефакты, логи, UI-рендер, опциональные preview.
- `C/L⊥`: индикатор согласованности уровней (не контроллер).

## 8) Альтернативы

### A1) Всегда публиковать state blob

Плюсы: просто, удобно для отладки.  
Минусы: ломает GPU-first, создаёт “точку касания” модели, увеличивает I/O, плохо масштабируется.  
Решение: запрещено по умолчанию; допускается только explicit/opt-in.

### A2) Делать GPU IPC между процессами (CUDA shared memory)

Плюсы: подписчики могли бы читать GPU-данные напрямую.  
Минусы: сложность, платформенные риски, слабая переносимость; не нужен на первом этапе.  
Решение: отложено.

## 9) Точки бифуркации (самое важное)

- BIF-01: Публикация state
  - варианты: always | opt-in | never
  - выбранное: opt-in
  - критерии: сохранение канона “наблюдение не вмешивается”

- BIF-02: Транспорт артефактов
  - варианты: tcp | shm/mmap | file
  - выбранное сейчас: tcp как прототип; shm/mmap — целевой

- BIF-03: Базовый тик запуска
  - варианты: `GlobalTick(L0)` | `BaseTick(Lmin)`
  - выбранное: `BaseTick(Lmin)` допустим в запуске, координата `(base_level, tick)` фиксируется в API

- BIF-04: “two strikes”
  - варианты: tuning | change level/alphabet
  - выбранное: 2‑й провал класса → смена пространства решений

---

## 10) Границы применимости

- В хаотических режимах без инвариантов `OuterFields` и консенсусные метрики будут “плохими” — это ожидаемо.
- В режимах перегруза уровень должен сигнализировать `instability/budget_pressure`, а не “маскировать” проблему.

---

## 11) Риски и предохранители

Риски:
- неявные CPU-копии полей через диагностику/виз;
- дрейф терминов `L0` vs “консенсус” (лечится введением `C/L⊥` как отдельного понятия);
- подмена “видимых метрик” хрупкими артефакт-детекторами.

Предохранители:
- `observables_mode` (opt-in для тяжёлых CPU-анализов),
- метрики по классам периодов/уровней,
- “two strikes — change dimension”.

---

## 12) План внедрения (кратко)

1) GPU-first observables (без CPU-копий по умолчанию).
2) `OuterFields` V1 как артефакт.
3) napari как подписчик артефактов.
4) `consensus_error` как артефакт согласования уровней.
